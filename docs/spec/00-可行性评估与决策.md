# 00. 可行性评估与决策

## 1. 结论

项目可行，适合按“单平台、单设备、离线优先”实施。最大的技术风险不是公式库、计时或本地统计，而是魔域 V10 AI 不同固件批次的蓝牙握手、四元数坐标映射及长时间事件一致性。因此必须先完成真实硬件协议验证，再承诺完整三维复盘。

综合判断：

| 模块 | 可行度 | 难度 | 主要依据与约束 |
|---|---:|---:|---|
| 119 个 CFOP 公式库 | 95% | 低至中 | 数据结构和渲染成熟；需独立整理素材和验证公式 |
| 训练与熟练度管理 | 95% | 中 | 完全离线，规则明确 |
| 手动计时与统计 | 95% | 中 | 技术成熟；需把 WCA 式操作和误触处理做稳 |
| V10 AI 转动读取 | 85% | 中 | 已有公开实现；仍须核对真机名、固件和丢包行为 |
| V10 AI 四元数读取 | 80% | 中至高 | 已有 0xAC 开启陀螺仪与 0xAB 数据解析实现；坐标和漂移需实测 |
| 实时三维数字孪生 | 85% | 中至高 | move 更新局面、gyro 更新整体朝向，二者需严格分离 |
| CFOP 自动分段 | 80% | 高 | 可用状态谓词确定阶段，但 X-cross、回退、跳 OLL/PLL 需覆盖 |
| 精准“思路诊断” | 55% | 很高 | 停顿和动作可量化；“看ahead、换手”等只能做启发式判断 |
| 小圈子 APK 分享 | 95% | 低 | 技术简单；签名密钥、升级和 GPL 源码分发必须规范 |

这里的百分比表示“在本文限定范围内完成可靠版本”的工程把握，不是统计学概率。

## 2. 对 V10 AI 协议认知的修正

用户关于“可以拿到四元数”的判断基本正确；关于“没有加密”需要修正：

- 同族设备通常以 WCU_MY32_XXXX 一类名称广播。
- 公开实现使用固定基础密钥和设备 MAC 派生 AES key / IV。
- 常见服务 UUID 为 0783b03e-7735-b5a0-1760-a305d2795cb0，读写特征末尾分别为 cb1 与 cb2。
- 0xAC 指令用于开启陀螺仪通知，0xAB 消息包含四元数。
- 四个有符号 32 位整数按 2 的 30 次方缩放，再归一化得到 w、x、y、z。

因此，这不是明文、零处理的 BLE 数据，但协议已经有可研究和移植的实现，工程上不构成阻断。具体字节序、轴向、符号和固件差异必须以用户的 V10 AI 真机为准。

## 3. 设计合理性评估

### 3.1 合理的部分

- 公式库、训练、智能魔方和复盘不是四个孤立功能，它们能形成闭环：

    记录中发现薄弱阶段 → 定位 case → 选择或修改公式 → 训练 → 再次实拧验证

- 离线优先符合自用场景，免去账号、服务器、隐私政策和长期运维负担。
- 首版只支持 V10 AI，能把蓝牙兼容矩阵压缩到可控范围。
- 使用结构化局面和程序生成示意图，比裁切参考海报更清晰、可检索，也更合规。
- 把真实转动和四元数一并保存，能同时支持精确局面回放和直观手持朝向回放。

### 3.2 必须收敛的部分

- “各家智能魔方 APP 的所有能力”不能作为首版目标。设备品牌、协议、固件和坐标系差异会拖垮稳定性。
- “像 Smart Player Pro 一样”只能作为体验方向，不能直接等同于首版验收范围。
- 首版复盘应承诺客观指标：动作、时间、阶段、停顿、TPS、步数、转体；不承诺从单个魔方的陀螺仪准确判断换手、手指动作或视线。
- 首版先做白底 CFOP。色中、盲拧、多阶、RouX、ZZ 和相机识别均推迟。
- 三维渲染不应承担业务状态计算；它只展示由核心魔方引擎给出的状态。

## 4. 推荐产品边界

### 首个可分享版本包含

- 119 个 CFOP 预设 case 与可编辑公式变体。
- 收藏、标签、搜索、首选公式、笔记和掌握度。
- 公式三维演示与逐步播放。
- 识别训练、公式执行训练、手动计时。
- V10 AI 扫描、连接、电量、局面、move 和四元数读取。
- 实时三维显示、重新校准、自动重连和状态重同步。
- 成绩会话、WCA 式 +2 / DNF、ao5 / ao12 / ao100。
- 完整时间轴回放、CFOP 阶段时间、步数、TPS 和停顿。
- 本地备份、恢复、诊断导出和 APK 升级保留数据。

### 明确非目标

- 云账号、云同步、排行榜、社交动态和广告。
- iOS、网页正式版、桌面正式版。
- V10 AI 以外的智能魔方。
- 摄像头识别或手部动作识别。
- 在线对战和 WCA 赛事计时替代。
- 自动判定“最佳公式”或生成带权威口吻的 AI 教练结论。
- 后台持续扫描蓝牙或应用退出后继续记录。

## 5. 技术路线决策

| 层 | 选择 | 原因 |
|---|---|---|
| 客户端 | Kotlin + Jetpack Compose | Android 原生 BLE、生命周期和权限控制更稳 |
| 数据 | Room / SQLite | 离线、可迁移、可测试，适合关系数据 |
| 异步 | Kotlin Coroutines + Flow | BLE 事件、计时和 UI 状态统一 |
| 魔方引擎 | Kotlin 领域层 | 状态计算和复盘不可依赖 WebView |
| 三维渲染 | 本地受限 WebView + 未修改的 cubing.js | 公式和魔方渲染成熟，降低自研 WebGL 成本 |
| 缩略图 | 原生 Canvas 或预生成本地资源 | 列表性能更稳定，不为每张卡片启动三维视图 |
| 蓝牙 | Android 原生 GATT | 比 Web Bluetooth 更适合可安装 APK |
| 备份 | 带校验清单的单文件压缩包 | 方便用户离线保存和朋友间迁移 |
| 网络权限 | 不声明 INTERNET | 从权限层面兑现“完全离线” |

WebView 只能加载应用内可信资源，关闭任意 URL 导航和文件访问；原生与网页之间只传递经过 schema 校验的局面、动作和视角消息。

## 6. 开源与素材决策

推荐项目整体使用 GPL-3.0-only，原因如下：

- csTimer 和 Twisty Timer 都是 GPL-3.0；复用其受版权保护的代码或数据后，分发组合程序需满足 GPL。
- “只发给几十位朋友”仍属于分发，接收者应获得对应源码、许可证和再分发权。
- GPL 不要求必须把源码公开到互联网；可随 APK 提供源码压缩包或让所有接收者能访问源码仓库。
- cubing.js 的 MPL-2.0 和相关 MIT 依赖可在保留通知、满足各自条款的前提下使用。

合规不是产品负担，首版只要把许可证、第三方通知、构建方法、源码归档和签名版本关联自动化即可。详细规则见 07 文档。

## 7. Go / No-Go 闸门

### G0：协议可行

必须在用户的真机上同时满足：

- 能稳定发现并连接目标设备。
- 能取得固件信息、电量和完整 facelet 状态。
- 能连续接收 move，序号异常可检测。
- 能开启 gyro 并解析有效、归一化的四元数。
- 三个物理轴方向完成标定，静置无明显跳变。
- 20 次完整复原中，最终局面与真实魔方一致；不一致时能自动请求全量状态恢复。

任何一项失败，都先修协议层，不进入完整 UI 开发。

### G1：核心闭环可用

- 公式可浏览、编辑、校验和训练。
- 手动计时和智能魔方计时均能形成 Solve 记录。
- Solve 可重放，统计可由事件重新生成。
- 飞行模式下所有功能正常。

### G2：可安全分享

- 升级安装不丢数据。
- 备份恢复通过往返校验。
- APK、源码包和许可证版本一一对应。
- 三台不同性能 Android 真机通过核心回归。

## 8. 工期量级

以一名开发者配合 Codex、能持续拿到 V10 AI 真机测试为前提：

| 阶段 | 量级 | 说明 |
|---|---:|---|
| 协议验证 | 3–7 个专注工作日 | 最大不确定项 |
| 公式库、训练、手动计时 | 2–4 周 | 包括内容校验与交互打磨 |
| 智能魔方实时跟踪 | 2–4 周 | 包括重连、校准、丢包和 WebView 通信 |
| 复盘、CFOP 分段与统计 | 3–6 周 | 依赖测试语料和多轮真机验证 |
| 备份、合规、发布验收 | 1–2 周 | 包括多设备升级测试 |

整体约 8–14 个专注周。AI 可以加快实现，但不能替代真机协议验证、公式内容审核和长期数据一致性测试。

## 9. 主要风险登记

| 风险 | 影响 | 应对 |
|---|---|---|
| V10 AI 固件或广播名不同 | 无法连接 | 先读取服务和固件，协议按能力探测，不只按名称判断 |
| Android 无法取得公开 MAC | 无法派生密钥 | 支持设备名后缀推导、扫描结果地址与手动输入三种来源，并校验握手 |
| move 丢包或乱序 | 局面错误 | 保存序号，发现空洞立即标记并请求全量 facelet |
| 四元数轴向或手性错误 | 画面反向或漂移 | 建立设备 profile 标定矩阵和可复现轴向测试 |
| gyro 采样量过大 | 数据库膨胀 | 分段压缩保存、可配置采样降频，调试原始包限额保留 |
| CFOP 分段误判 | 统计误导 | 状态谓词、置信度、分析器版本和人工修正并存 |
| 复制图片或 UI | 版权与辨识度风险 | 所有 case 图由状态生成，采用独立视觉系统 |
| GPL 文件漏发 | 分发不合规 | 发布任务自动生成源码包和第三方通知清单 |
| 签名密钥丢失 | 无法覆盖升级 | 离线双份加密备份签名材料并记录恢复流程 |

## 10. 最终建议

建议立项，但按“协议验证 → 核心学习闭环 → 智能实拧 → 深度复盘”的顺序推进。最不合理的做法是先把所有页面画完再测试设备；最合理的第一份代码，是一个小而透明的 V10 AI 协议验证应用。
