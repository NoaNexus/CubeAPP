# 05. V10 AI 蓝牙与三维跟踪规范

## 1. 目标与边界

本规范只覆盖魔域威龙 V10 AI 及其确认兼容的同协议固件。目标是：

- 读取设备信息、电量和完整局面。
- 连续读取每一步层转动。
- 开启并读取陀螺仪四元数。
- 将层状态与整体手持朝向合成为实时三维显示。
- 检测事件空洞并恢复可信状态。

不提供：

- 改名、灯光、震动、恢复出厂或固件升级。
- 对其他魔域或其他品牌设备的“猜测式兼容”。
- 应用退出后的后台扫描和长期连接。

## 2. 已知协议事实

来自 csTimer 和 smartcube-web-bluetooth 的公开实现：

| 项目 | 已知值或行为 |
|---|---|
| 广播名 | 常见前缀 WCU_MY32_ 或 WCU_MY3；不得只靠名称认定能力 |
| 主服务 | 0783b03e-7735-b5a0-1760-a305d2795cb0 |
| 通知 / 读取特征 | 同一 UUID 族，末尾 cb1 |
| 写入特征 | 同一 UUID 族，末尾 cb2 |
| 加密 | 与 GAN Gen2 / Gen3 同类的 AES 数据包装；key / IV 由公开基础值和设备 MAC 派生 |
| 设备信息消息 | 0xA1（十进制 161） |
| 完整局面消息 | 0xA3（163） |
| 电量消息 | 0xA4（164） |
| move 消息 | 0xA5（165） |
| gyro 消息 | 0xAB（171） |
| gyro 控制 | 0xAC（172）开启或配置通知 |

关键结论：协议可实现，但不是“完全无加密的明文”。应用必须把公开实现移植为有测试向量的独立协议模块，不能假定任意 BLE 包都能直接解释。

资料：

- [csTimer moyu32cube.js](https://github.com/cs0x7f/cstimer/blob/master/src/js/hardware/moyu32cube.js)
- [smartcube-web-bluetooth moyu32.ts](https://github.com/poliva/smartcube-web-bluetooth/blob/main/src/smartcube/protocols/moyu32.ts)

真实硬件的广播名、固件、服务、消息长度和频率必须写入协议验证记录。

## 3. 设备识别

扫描筛选分两级：

1. 粗筛：附近 BLE 设备名匹配已知前缀，或用户从全部结果中选择。
2. 能力验证：连接后发现目标服务与特征，完成解密握手并取得有效设备信息。

只有第二级成功，UI 才显示“支持的 V10 AI”。名称匹配但握手失败的设备显示“未验证”，不得持续发送试探写入。

设备唯一性按以下优先级建立：

- Android BluetoothDevice 地址。
- 广播名中的地址后缀。
- 用户手动确认的设备 MAC。
- 设备信息和最近握手特征的组合摘要。

由于 Android 或设备可能使用随机地址，任何地址来源都要记录 source，并用成功解密作为最终校验。

## 4. Android 权限流程

Android 12 及以上：

- 在开始扫描时申请 BLUETOOTH_SCAN。
- 在连接前申请 BLUETOOTH_CONNECT。
- 若不把扫描结果用于位置，使用 neverForLocation 声明。

Android 11 及以下：

- 按官方兼容规则声明旧蓝牙权限。
- 只有系统确实要求扫描位置权限时才申请，并用 maxSdkVersion 30 限制。

拒绝权限不会阻断公式库和手动计时。设备入口保留“为什么需要”和系统设置跳转。

参考：[Android 蓝牙权限](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)。

## 5. 安全写入白名单

Release 版本的协议层只允许下列目的：

| 目的 | 条件 |
|---|---|
| 请求设备信息 | 握手阶段，固定长度 |
| 请求完整 facelet 状态 | 初次连接、用户手动同步或发现 gap |
| 请求电量 | 初次连接及低频刷新 |
| 开启 / 关闭 gyro 通知 | 进入或离开需要三维朝向的前台页面 |

实现要求：

- 每种写入由强类型 command 构造，不接受 UI 传来的任意 byte array。
- opcode、长度、状态和频率均校验。
- 未知命令在编译期和运行期默认拒绝。
- 调试页也不能提供“发送任意十六进制”的输入框。
- 禁止设备重命名、校准写回、恢复、固件和未审查控制指令。

具体请求包格式以移植实现和真机抓取的测试向量为准；本文的消息类型不是允许盲发的完整字节串。

## 6. 握手流程

    扫描
      → 连接 GATT
      → 发现服务与 cb1 / cb2
      → 订阅 cb1 通知
      → 确定 MAC 来源
      → 派生 AES key / IV
      → 请求设备信息
      → 请求完整局面
      → 请求电量
      → 开启 gyro
      → 校验首个 move 与四元数
      → Ready

每步具有：

- 进入条件。
- 5–10 秒明确超时。
- 最多有限次数重试。
- 可诊断的失败码。
- 生命周期取消。

不得同时向 BluetoothGatt 排队多个未完成写入。所有 descriptor 和 characteristic 操作经单一串行队列。

## 7. 解密与消息解析

协议实现分为纯 Kotlin、无 Android 依赖的四层：

1. KeyDeriver：由经过规范化的 MAC 产生 key / IV。
2. PacketCipher：解密 RX、加密 TX，包含长度和块边界测试。
3. MessageDecoder：按 type 和长度解析为协议 DTO。
4. MoyuV10Adapter：转换为 APP 统一事件。

必须建立测试向量：

- 已知 MAC → 预期 key / IV。
- 已知加密包 → 预期明文。
- 已知明文请求 → 预期加密包。
- 每种消息的正常、最短、截断、未知 type 和校验失败样本。

不得把解密异常吞掉后继续按明文解析。连续异常达到阈值时断开并显示“设备识别失败”。

## 8. move 处理

### 8.1 顺序

对每个 move：

1. 解密并校验包长。
2. 读取设备序号和设备时间（若有）。
3. 按协议规定的模数检查前后序号。
4. 映射到统一 move。
5. 使用 CubeEngine 应用到最后可信状态。
6. 写入内存 Solve 缓冲。
7. 通知计时状态机和渲染器。

任何层都不得为保持动画流畅而丢弃 move。

### 8.2 gap 与恢复

发生以下任一情况进入 Syncing：

- 序号空洞或无法解释的逆序。
- move 不能应用到当前模型。
- FaceletSnapshot 与推导局面不同。
- 解密连续失败。
- 重连后第一条事件无法与旧 epoch 衔接。

恢复流程：

1. 写入 SyncGapEvent。
2. 停止对外宣称“状态已同步”。
3. 请求完整 facelet。
4. 比较推导状态与设备状态。
5. 以设备快照建立新 checkpoint 和 sequence epoch。
6. 继续记录；受影响区间标记 incomplete。

不得用猜测的动作填补空洞。

## 9. 四元数解析

公开实现中的 0xAB 消息按以下结构读取：

- offset 1：w，little-endian int32。
- offset 5：x，little-endian int32。
- offset 9：y，little-endian int32。
- offset 13：z，little-endian int32。
- 每个值除以 2 的 30 次方。
- 计算长度并归一化。

输入验证：

- 消息长度足够。
- 四个值均为有限数。
- 归一化前长度处于合理范围；过小或异常大则丢弃并计数。
- 归一化后长度误差在容许范围。

连续性处理：

- q 与负 q 表示同一姿态。
- 若当前 q 与前一 q 的点积小于 0，将当前 q 整体取负。
- 渲染插值使用 SLERP，不逐分量线性插值。
- 逻辑保存归一化原值；平滑只作用于展示轨迹，不能覆盖原始规范化样本。

## 10. 坐标和校准

设备坐标、Android 逻辑坐标和 WebGL 坐标可能具有不同：

- 轴顺序。
- 正方向。
- 左手 / 右手系。
- 四元数分量顺序。
- body-to-world 或 world-to-body 含义。

因此，首次连接必须标定，不允许仅凭视觉试到“差不多”。

### 10.1 标定数据

CalibrationProfile 保存：

- axisMapping：3 × 3 正交映射或等价枚举。
- handedness / inversion。
- componentOrder。
- referenceQuaternion。
- firmware 与协议版本。
- verifiedAt。

### 10.2 三步验证

1. 黄上蓝前静置，记录 reference；白色 Cross 位于 D 面。
2. 整体向用户右侧旋转约 90°，验证期望轴和符号。
3. 整体向前翻转约 90°，验证第二轴；第三轴由正交关系确认。

只有两次方向和幅度都在阈值内才保存 profile。失败时回到锁定视角，move 功能仍可使用。

### 10.3 显示姿态

若实测证明设备四元数表示 body-to-world，可按以下概念计算：

    qRelative = inverse(qReference) × qMappedDevice
    qDisplay = qSceneCorrection × qRelative

若设备定义相反则先取 inverse。最终顺序必须由三个轴向自动化测试和真机视频对照决定，不能仅凭公式名称假定。

## 11. 层状态与整体朝向必须分离

系统维护两个独立状态：

- CubeState：54 facelet 或 cubie permutation / orientation，由 move 改变。
- PhysicalOrientation：整个魔方在空间中的四元数，由 gyro 改变。

三维输出：

    scene = PhysicalOrientation × Render(CubeState)

原则：

- 手里整体转动魔方不会改变 CubeState。
- R、U 等层转动改变 CubeState，同时设备姿态可能有轻微运动；二者不能互相抵消。
- 公式语义使用面中心定义，不随摄像机视角改变。
- 用户锁定视角时，只冻结 PhysicalOrientation 的展示，不停止保存 gyro。

## 12. gyro 渲染与采样

- BLE 收到样本后立即归一化并进入最新值缓存。
- 渲染器按屏幕帧率拉取最新姿态，不逐包排队播放。
- 相邻样本做 SLERP；插值窗口以不明显增加延迟为准，建议从 20–40 ms 实测。
- 页面不可见时停止 WebView 帧更新。
- 记录层默认最高 50 Hz，动作发生前后强制关键帧。
- 长时间静止时允许降采样。

延迟预算建议：

| 环节 | P95 预算 |
|---|---:|
| BLE 到解析完成 | 30 ms |
| 事件分发与状态更新 | 15 ms |
| 原生到渲染桥 | 20 ms |
| 下一帧显示 | 35 ms |
| 合计 | 目标小于 100 ms |

真机报告必须同时给中位数和 P95，不只记录“感觉跟手”。

## 13. 转体识别

转体次数来自 gyro 的启发式分析，不来自层 move：

- 将姿态投影到 24 个立方体正交方向。
- 使用角度阈值与滞回，避免手抖反复计数。
- 只有从一个稳定方向进入另一个稳定方向，并保持最短时间，才计一次 x / y / z 类转体。
- 中间任意角度手持不强行分类。
- 结果保存 confidence，并允许关闭或人工忽略。

首版不把 gyro 用于判断换手、regrip、手指或视线。

## 14. 三维渲染同步

每次 SetCubeState 和 ApplyMove 均携带单调 sequence：

- 渲染器报告最后应用的 sequence。
- 落后小于阈值时压缩动画时长。
- 落后超过阈值时直接发送全量 state，并从该 sequence 继续。
- 渲染错误不会回写或修改核心 CubeState。

回放 seek 不从头逐步播放全部 move：

1. 选择最近的 FaceletCheckpoint。
2. 在 Kotlin 引擎中快速应用到目标时刻。
3. 插值得到目标 orientation。
4. 一次 SetState + SetOrientation 更新渲染器。

## 15. 协议验证页

在正式产品 UI 前，建立仅供开发和验收的“V10 Lab”：

### 屏幕内容

- 扫描结果：名称、地址来源、RSSI、服务。
- 连接阶段与每步耗时。
- 设备信息、固件、电量、能力。
- 最近 50 个 RX / TX 包的时间、type、长度和脱敏 hex。
- 最近 move、sequence、设备时间和当前 facelet hash。
- 四元数原值、归一化值、频率和丢弃计数。
- 简单三维魔方与锁定 / 跟随切换。

### 操作

- 扫描、连接、断开。
- 请求信息、状态和电量。
- 开关 gyro。
- 设为正面和三轴验证。
- 导出诊断 JSON。

不提供任意字节写入。

## 16. 协议验收

### 基础

- 冷启动后 5 次连接均可完成握手。
- 设备在其他 APP 占用、蓝牙关闭、权限拒绝都有可理解结果。
- 电量和固件读取稳定。

### move

- 逐一验证 U D L R F B 的顺、逆、180°。
- 连续快速执行至少 500 个 move，sequence 统计完整。
- 20 次完整 scramble + solve，最终设备 facelet 与引擎一致。
- 人为中断连接后能检测 gap，并在 2 秒目标内尝试重同步。

### gyro

- 静置 30 秒无 q / -q 跳变造成的画面翻转。
- 三个轴各完成正负 90°，方向和幅度正确。
- 旋转 360° 后回到接近初始朝向。
- 层转时整体画面不错误地旋转一个整面。
- 锁定视角不影响 move 层状态。

### 安全

- Release 包不存在任意 opcode 或 raw write 入口。
- 断连、后台、横竖屏切换不会残留失控的 GATT 写队列。
- 诊断导出默认遮蔽完整设备地址和密钥材料。

## 17. 硬件差异处置

若用户真机与公开实现不同：

1. 保存广播、服务与加密前后诊断，不发送未知写入。
2. 比对固件和设备名。
3. 为 profile 增加明确版本，不在通用 decoder 中加入模糊猜测。
4. 新 profile 必须有独立测试向量和实测记录。
5. 无法获得 gyro 时，允许以“move 跟踪 + 锁定三维视角”降级，但在产品页明确说明。

只有 G0 验收全部通过，才把“V10 AI 四元数三维跟踪”标记为正式支持。
